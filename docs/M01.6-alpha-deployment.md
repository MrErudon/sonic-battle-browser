# M01.6 — Alpha deployment and polish

## Foundation and scope

Based on main `7222501dc797a7a25f7f25339647bd3282067e05`, merged PR #5.
M01.4 correction `132b566e9b53b6e1a0e646c40714062269200337` is included.
Baseline main CI was rerun for this milestone; all 211 tests, typecheck,
build, audit and 43 Chromium checks passed. The latter includes complete
player victory and CPU defeat/rematch flows on Easy, Normal and Hard.

Movement, combat, CPU and match controller are deliberately unchanged.
The original cyan/amber procedural artwork remains replaceable. HUD panels
have opaque backing and larger bars; normal play hides all fighter labels
to prevent overlap. Debug retains fighter states and coordinates. Countdown,
KO and result panels have stronger contrast; Fighting gets a brief visual cue.
Small/coarse-pointer layouts explicitly require a keyboard. Touch controls,
audio, gamepad, multiplayer, saves and new combat mechanics remain out of scope.

## Account authorization and private alpha rollout

Cloudflare account access and installation/authorization of the Cloudflare
Pages GitHub App are required. Restrict its repository access to this repository.
The current ChatGPT connection does not supply Cloudflare authorization.
Do not send passwords or API tokens in chat. An account owner must complete
interactive authorization or provide an approved connected Cloudflare tool.
No API token is necessary for the dashboard Git integration described here.

The creation wizard can deploy immediately when Save and Deploy is selected.
**Stop before that action until deployment and its visibility are approved.**
Keep automatic production and preview builds disabled during initial setup
where available. A later push or merge to main automatically deploys when
production builds are enabled; this is separate from GitHub CI and does not
wait for tests to finish. Require passing CI and review before merging.

Cloudflare's built-in preview Access setting protects
`*.<project>.pages.dev`; it does **not** by itself protect
`<project>.pages.dev`. Before an approved first release, prepare Access
applications for **both** exact production and wildcard preview hostnames,
with explicit allowed tester identities and no bypass policy. Use the official
Known issues instructions below if the Pages-generated Access application
needs its wildcard removed, then recreate preview protection. If the account
cannot configure protection before an initial build, leave deployment paused
and resolve that workflow with the account owner; do not publish temporarily
and assume an obscure URL is private. Custom domains are not part of this PR.

After deployment is explicitly approved:
1. Confirm the chosen Pages name and both Access applications. Confirm branch
   controls, Node, root, build and output settings from the table.
2. Connect this GitHub repository through Pages Git integration with main as
   production. Authorize only the intended repository. Trigger the approved
   build only when access controls and visibility are agreed.
3. In an anonymous session, test the production root, a hashed JS/CSS asset,
   a hash preview URL and its branch alias. They must require Access login
   or deny access; none should return game assets anonymously.
4. Sign in as an allowed tester. Confirm canvas, fonts/styles and assets load.
   Play menu → difficulty → countdown → fighting → KO → results → rematch.
   Check tab-away pause, help/Escape, resize and refresh.
5. Confirm deployed commit SHA equals the reviewed commit. Verify HTML cache
   and no-index headers, hashed asset cache and no runtime/network failures.
6. Enable same-repository PR previews only after wildcard Access is verified.
   Fork PRs do not get Pages Git previews. Record the private URLs in the
   approved release record, not a public PR comment.

There is no live URL in this PR. Deployment remains blocked on explicit approval,
Cloudflare authorization, verified private access and hosted URL smoke testing.
Public publication and custom domains need separate explicit approval.

## Validation and browser scope

Commands:
```sh
npm ci
npm test
npm run typecheck
npm run build
npm audit
npx playwright install --with-deps chromium firefox webkit
npm run test:browser
BROWSER=chromium npm run test:browser:production
BROWSER=firefox npm run test:browser:production
BROWSER=webkit npm run test:browser:production
npm run report:bundle
```

On PowerShell set `$env:BROWSER = "firefox"` before invoking the production script.
The production script requires dist from a preceding build and runs Vite preview
on loopback only. CI tests each engine independently and uploads screenshots,
JSON results, bundle sizes and the compiled alpha-dist artifact. It does not deploy.

The existing dev-server Chromium suite retains all M01.1–M01.5 coverage,
including legal-key player victories and CPU rematches on all presets,
short taps, focus/help, CPU jumping recovery, scene restart and listener cleanup.
The production matrix tests compiled assets with no imports of source modules
or hidden game handles: all menu/difficulty choices, attack input, help/blur,
a complete CPU match to defeat, rematch, score/health reset, and return to menu.
Clock acceleration changes browser time, not fighter state or statistics.
Simultaneous KOs and 2–1 results remain covered in unit tests rather than claimed
as end-to-end production browser scenarios.

Desktop viewport checks: 1920×1080, 1366×768, 1280×800, 1024×768 and 800×600.
Mobile-sized layouts: 390×844 and 844×390; coarse-pointer emulation verifies the
keyboard notice. These are desktop engine emulations, not certification on real
iPhone/Android hardware. Menus can scroll on compact windows. A hardware keyboard
is required to fight; mobile keyboard support and performance need real-device
testing before promising mobile play. WebKit is useful Safari-engine coverage,
not a substitute for testing shipping Safari on Apple hardware.

Final exact-head outcomes are recorded in PR #6 and its CI run. Local shell/network
limitations required repository changes through GitHub and execution in Actions.
Do not treat documentation of a command as evidence it passed; use CI artifacts.

## Performance and lifecycle

Vite separates the unchanged Phaser engine into a stable hashed chunk so UI-only
updates can reuse it. This is cache isolation, not a reduced cold download.
The existing >500 kB engine warning is retained, not suppressed. The bundle report
records raw and gzip JS/CSS bytes after every build. Initial download remains the
main known cost. Avoid a custom Phaser build or rendering rewrite in this milestone.
Later options: measure on low-end hardware, consider loading the engine after menu
entry, profile draw work and consider a documented subset build only if justified.

The pure simulation remains fixed at 60 Hz. Scene listeners are still removed on
shutdown. Scene restart and input cleanup are regression-tested in Chromium.
No new per-frame listeners, timers or gameplay callbacks were introduced. The
Fight cue is CSS-only and cannot advance combat; reduced-motion preference shortens it.
Browser startup/flow checks do not constitute FPS, memory-leak or load benchmarks.

## Rollback and emergency withdrawal

1. Pause production and preview branch builds to avoid an immediate redeploy.
2. In Pages Deployments, select the last verified successful **production**
   deployment and use Rollback; preview deployments are not production rollback
   targets. Verify its SHA, Access protection and menu/rematch flow.
3. Fix source via a reviewed revert/fix PR so the next main build does not
   reintroduce the issue. Rollback does not rewrite Git history.
4. Old hash and branch preview URLs can remain reachable. For withdrawal, keep
   Access denying testers while removing affected preview deployments/aliases
   and, if necessary, delete the Pages project through the approved account
   workflow. Disabling builds alone does not remove already deployed content.
5. Do not remove Access as part of troubleshooting or rollback. Test anonymous
   denial and authenticated asset loading again after any hostname/project change.
