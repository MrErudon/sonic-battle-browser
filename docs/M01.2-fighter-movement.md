# M01.2 — Fighter Movement

## Implementation

Based on main `ccbb253` (merged PR #1). `src/core/movement.ts` owns the
Phaser-independent fighter model and a deterministic 60 Hz step. The scene
adapts keyboard input and accumulates render time, capped at 100 ms per render
to avoid large catch-up bursts after stalls. No new dependencies.

Two original geometric training robots use the same simulation. P1 accepts
WASD or arrows and Space; P2 receives neutral input. Opposing keys cancel.
Jump presses are queued until the next simulation tick and consumed once.
Holding Space does not auto-jump. Focus loss clears keys and pending input.

### Lost-jump-input correction (PR #2, based on `59a37e5`)

The scene now listens to DOM `keydown` events for `code === "Space"` outside
`update()`. A press/release between renders therefore survives key release.
Events with `repeat === true` are ignored, including repeats received after blur.
The pending boolean coalesces multiple taps before a tick; it is retained across
renders with no simulation tick, passed to the first available tick, then cleared.
Later ticks in the same render receive no jump. No new input framework is added.

This is a queue until simulation consumption, not a gameplay jump buffer.
Airborne presses and presses consumed while landing recovery remains locked are
discarded, never saved until grounded. Existing movement semantics are unchanged:
on the tick that `landingRemaining` reaches zero, recovery ends and a new press
can jump. Eligibility is evaluated at consumption, not at DOM event time.

Window blur and Phaser game blur both reset held movement keys, pending jump,
and the partial-tick accumulator. Shutdown removes both DOM listeners and the
game blur listener, and clears input. Scene restart installs fresh listeners.
Broader combat/input architecture remains deferred to M01.3.

Movement input is screen-relative: Up moves toward the top of the display.
The inverse isometric projection maps input into arena coordinates, then the
result is normalized. Every direction has the same speed in **arena units**;
projected pixel speed varies with perspective. Facing uses eight screen compass
directions and persists at rest, including when pushing against a wall.

The footprint clamps to each boundary using its radius, both grounded and
airborne. It slides along edges. Jump height and vertical velocity are separate
from the ground position; there is one jump, reduced air steering, and no drift
when input is released. Landing locks movement for the configured recovery.
States are `idle`, `walk`, `jump` (ascending and descending), and `landing`.
Walking describes actual displacement, so a fully blocked fighter becomes idle.

`src/rendering/FighterView.ts` owns all artwork. Feet anchor to projected ground
coordinates, body height is subtracted from screen Y, and body depth always uses
projected ground Y. Shadows remain on the ground, below all fighters. Walking
animates feet; landing squashes the body; a visor and marker show facing. Labels
show each fighter's state and direction for review.

## Consulted specs and provisional decisions

- Chat 02: “2 Combat mechanics recreation”, Milestone 1 Combat Mechanics
  Specification v0.1. Adopted fixed 60 Hz, x/y plus z, normalized movement,
  immediate movement, reduced air steering, footprint bounds, single jump,
  and rendering-independent simulation. Its interactive tuning widget did not
  expose numerical movement values in the retrieved text.
- Chat 03: “3 Art Animation UI Planning”, Milestone 1 Art & Animation Pipeline
  v0.1. Adopted original replaceable artwork, eight logical directions, separate
  ground shadows, and ground-based depth sorting independent of jump height.
- Keep the merged 680 × 420 arena and 960 × 640 canvas rather than changing
  the foundation to the specs' proposed 640 × 400 / 320 × 240 dimensions.
- Defaults: speed 220 units/s, air multiplier 0.7, jump velocity 360 units/s,
  gravity 1000 units/s², radius 16 units, recovery 6 ticks (100 ms).
  These are prototype choices, **not measured GBA values**. Pass a per-fighter
  `MovementConfig` to `stepFighter` to tune them. Configuration is trusted static
  game data: use nonnegative speed/radius, positive gravity/jump speed, an air
  multiplier in [0, 1], and a nonnegative integer recovery frame count.
- Procedural graphics are temporary substitutes for the proposed 64 × 64
  sprite sheets and authored animation manifests. All eight directions render,
  but sprite atlases, art-frame counts, and final animation assets are deferred.
  Rendering can be replaced without changing simulation or input.
- Dash, fighter-body collision, combat, health, CPU decisions, character-specific
  air actions, touch input, and attack animation events belong to later work.
  Fighters can overlap in this milestone to inspect depth sorting.

## Manual review

1. `npm ci`, then `npm run dev`; focus the game.
2. Move in all eight directions with WASD and arrows. Release to stop; verify
   the facing label persists. Hold opposite directions to cancel movement.
3. Move against all arena edges, then along them; feet must stay inside.
4. Press Space, steer while airborne, release movement, then land. Hold Space
   through landing: there must be no automatic second jump.
5. Cross in front of and behind P2, then jump near it: draw order must follow
   the ground position and the shadow must stay on the floor.
6. Switch focus while holding a movement key; return and verify no stuck input.
7. Confirm P2 remains at its spawn throughout.
